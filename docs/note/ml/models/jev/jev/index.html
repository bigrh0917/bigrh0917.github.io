    What Is Jev?#

    Jev is a closed “System One” model from TypeSafe AI, in early access since September 2026. It does not chat or write. You give it a piece of text and a set of typed questions, and it returns a probability for each allowed answer from a single forward pass, so software can act on the result directly.

    This note looks at it from three sides:

    • Business angle: what problem it solves, who it replaces, and why a market formed around it.
    • Technical angle: how a model can answer without generating, and why calibration is the part that matters.
    • Taking it further: what I tried after rebuilding a small Japanese version, and what is still open.

    The rebuild itself is a separate write-up: japanese-jev.

    Numbers attributed to other people are as they reported them. I have not re-measured them. Numbers from my own runs say so.

    Business Angle#

    The Problem#

    Software is full of small decisions: which department gets this email, is this ticket urgent, does a human need to look at it, which tool should the agent call next. Before Jev there were three ways to make them.

    ApproachHow it worksWhere it falls short
    PeopleStaff read and sortExpensive and slow
    Rulesif/else on keywords and fieldsBreaks on anything the rules did not foresee
    A general LLMThe model reads the input and writes an answerThe answer has to be generated, parsed and checked; cost and latency are high

    The third one is the interesting case. A support system that receives 100,000 emails a day does not need 100,000 paragraphs. It needs 100,000 labels it can trust. With a completion API the model reads the input, writes text, the program parses the text, validates the JSON, and only then acts. Most of that work exists only because the model was built to write.

    What TypeSafe Sells#

    Jev turns unstructured input into typed decisions with probabilities. The question TypeSafe asks is whether a simple task needs a large model at all.

    JevFrontier LLMs
    Price$0.042 per million input tokens, output free$0.20 to $10 per million input tokens, output about 5x that
    Latency70 to 500 ms end to end3 to 329 s

    TypeSafe’s own claim is 40 to 200 times faster at equal intelligence, and 193.6 times faster and 444.6 times cheaper in its own evaluation.

    The company went into early access on 15 September 2026 and announced a $40M seed round the same day (led by DCVC, valuation about $200M). On 9 October it announced an $870M Series A led by a16z at a $7.5B valuation.

    What It Replaces#

    Not GPT or Claude. It replaces rerankers, traditional text classifiers, and the mid-size LLMs that sit in agent pipelines as decision nodes. Typical uses are model routing, tool selection, content moderation, agent guardrails, and scoring or reranking at scale.

    Why There Is a Market#

    The argument is the Jevons paradox: when a decision gets cheap, people make more of them. Places where an AI judgment used to be too expensive to bother with can now have one.

    Two Months Later#

    “Decision model” became a product category within two months of the launch.

    • OpenAI shipped a Decisions API on 6 October at $0.10 per million tokens. Its lead said publicly that Jev inspired it.
    • Cloudflare released Clef (Qwen3.8-27B base) and Clef-flash (Qwen3.5-9B base) with open weights under Apache-2.0 and a Jev-compatible API.
    • AWS open-sourced Decider 2B (Qwen3.5-2B base), which runs locally.
    • The open-source community produced more than a dozen reproductions.

    Weak Points#

    Commercial. The technical barrier is low. Someone reproduced the basic behavior in about 25 lines of code, and the large vendors followed within weeks.

    Technical.

    • It is opaque. The architecture is not public, so nobody outside can audit where a probability comes from. It never returns a malformed answer, but it can be confidently wrong.
    • On Banking77 (77 intents) a fine-tuned BERT scores 88.0% and Jev 76.4%.
    • Renaming the options from 0/1 to no/yes dropped AUC from .94 to .23.
    • It leans toward the first option, reads literally, and is unreliable at counting and comparing dates.
    • By default the state is not treated as hostile input.

    My Takeaway#

    Jev did not win by being smarter. It picked one task shape that everyone had ignored and optimized it as far as it would go. That shape was a latent need nobody served, because the whole field was busy with the intelligence race.

    Technical Angle#

    Jev’s internals are not public. What follows is the public interface, what black-box probing suggests, and how the open reproductions get the same behavior. In one line: a language model that only does prefill (one forward pass, no decoding), a readout that takes a softmax over the allowed answers, and temperature calibration.

    The Interface#

    A request carries one state and a set of questions. Each question has a type, an instruction, and its allowed answers.

    {
  "model": "jev-1.14.0",
  "state": "The left earbud I bought last week has no sound. I want to return it.",
  "questions": {
    "intent": {
      "type": "choice",
      "instructions": "What does the customer want?",
      "criteria": {
        "refund": "return the item for a refund",
        "repair": "have it repaired",
        "question": "ask for information"
      }
    }
  }
}

    There are three question types, called primitives.

    PrimitiveQuestion formReturnsTypical use
    ChoicePick one of 2 to 255 optionsThe selected option, a probability per option (summing to 1), a confidenceRouting, classification, tool selection
    ScoreAn ordinal scale of 2 to 10 levelsA probability-weighted expected score, a probability per levelPriority, risk, quality
    NoulOne yes/no propositionA probability between 0 and 1Flags, gates, independent checks

    The confidence is computed, not learned: (p_max − 1/n) / (1 − 1/n), where n is the number of options. It is 1 when all probability sits on one option and 0 for a uniform distribution.

    How a Request Flows#

    The structure of the answer is fixed before the model looks at the input. That is the main difference from a general LLM.

    graph LR
    A[State: the text to judge] --> C[One forward pass]
    B[Questions: defined by the developer] --> C
    C --> D[Logits of the allowed answers only]
    D --> E[Divide by temperature, softmax]
    E --> F[Typed result + probability]
    F -->|confidence above threshold| G[Software acts on it]
    F -->|below threshold| H[Hand to a person or a larger model]

    Take one support message: “My account was charged twice yesterday. I have contacted support three times and it is still not fixed.”

    1. State. The message is the state. A state is whatever needs judging, and it can also include the user’s history, the order status, business data or the current system state.

    2. Questions. The developer decides in advance what to ask. The model does not choose what to think about.

    QuestionAllowed answers
    What kind of problem is this?shipping, refund, product quality
    What is the customer’s mood?calm, dissatisfied, angry
    Does a person need to step in?yes, no
    Should it be escalated?yes, no

    3. Parallel evaluation. All four questions are answered against the same state in one request. There is no need to finish question 1 before calling the model again for question 2.

    4. Typed results with probabilities. Each answer comes back in the declared type, with a probability.

    {
  "category": "refund",
  "emotion": "angry",
  "needs_human": true,
  "escalate": true
}

    5. Execution. The software reads the result and acts: assign the ticket to the right team, raise its priority, notify an agent. The model decides; the software does.

    A probability of 0.96 does not by itself mean the answer is right 96% of the time. Whether it does is exactly what calibration is about. When it does, the software can set tiers: act automatically at high confidence, send to a review queue in the middle, hand to a person at the bottom.

    Three things make this work: the answer range is limited, so there is no free-form output to handle; one state serves many questions; and the probability gives the program something to set a threshold on.

    Why It Is Fast#

    A chat model asked to classify something emits tokens one at a time: a few hundred tokens of reasoning, then “The answer is B because…”. Every token is another pass over the weights (the bottleneck is memory bandwidth, not compute), and the only useful output is the “B”.

    A System One model is trained so that the next token after the prompt is the answer. At inference nothing is generated. The prompt goes through once, all its tokens in parallel, and the logits at the last position are read. The “B” is never even sampled, and there is no reasoning, no explanation, no end-of-sequence token. One decision costs about one forward pass instead of a few hundred.

    Two more things follow from this:

    • The format cannot break. Scores are only read for the allowed answers, so there is nothing to parse.
    • Questions can share the state. If the state is encoded once and kept in the KV cache, each question is a short suffix. TypeSafe’s cookbook reports that 13 questions in one request are 10 times faster than 13 separate calls.

    It is fast compared with making an LLM generate a classification. It is not faster than a BERT-style classifier. The advantage over those is that the labels live in the prompt and can change per request without retraining. Training itself is not faster either: it is the usual forward and backward pass.

    Calibration Is the Product#

    A System One model is used with a threshold: above 0.9 act automatically, otherwise send to a person. That rule only means something if the probabilities are honest. Accuracy says whether the model can do the questions. Calibration says whether the model knows which questions it cannot do. A classifier needs only the first. A System One model sells the second.

    ECE#

    Think of a weather forecaster who says “70% chance of rain tomorrow”. One day cannot tell you whether to trust him. Collect every day he said 70%: if it rained on about 70% of them he is calibrated, if it rained on 40% he is bragging, and if it rained on 95% he is too cautious.

    ECE (expected calibration error) does the same for a model. Group the predictions by stated confidence, compare the average confidence with the actual accuracy in each group, and take the weighted average of the gaps. An ECE of 0.05 reads as “its stated confidence is off by 5 points on average”. The standard version uses 15 groups; three are enough to see the idea.

    A well-calibrated model on 100 questions:

    GroupConfidence rangeQuestionsMean confidenceActual accuracyGap
    Low0.3–0.6100.500.500.00
    Mid0.6–0.9300.750.730.02
    High0.9–1.0600.950.930.02

    ECE = (10 × 0.00 + 30 × 0.02 + 60 × 0.02) / 100 = 0.018. Of the 60 questions it called at 0.95, 56 were right.

    An untrained model on 100 questions:

    GroupConfidence rangeQuestionsMean confidenceActual accuracyGap
    Low0.3–0.630.550.670.12
    Mid0.6–0.9120.800.580.22
    High0.9–1.0850.960.620.34

    ECE ≈ 0.32. It claims 96% on 85 questions and gets 53 right. A rule of “above 0.9, act” lets 85 answers through with 32 errors. The calibrated model lets 60 through with 4.

    With a low ECE the threshold has a definite meaning: if the business can accept 2% errors, raise the line to 0.98. With a high ECE the line means nothing, and moving it does not control the error rate.

    Why an Untrained Model’s Numbers Cannot Be Trusted#

    A pretrained language model answers “what usually follows text like this”, not “is A correct”. The two are often related, which is why zero training works at all, but they are not the same question.

    • Letters have priors. In the corpus, A follows an option list more often than D.
    • Probability leaks to other tokens. An untrained model may want a newline or “The answer is” at that position. If A to D hold 5% of the mass and the rest is thrown away, 0.03 and 0.01 renormalize to 0.75 and 0.25. That 0.75 is a ratio of two small numbers and says nothing about how sure the model is.
    • It is confident about format, not content. Pretraining produces very sharp distributions when continuing a fixed format. Sharp is not the same as right.
    • Nobody asked it to be calibrated. Nothing in pretraining says “when you say 80%, be right 80% of the time”.

    What Training and Calibration Each Fix#

    Fine-tuning makes “the next token’s probability” and “the judgment” the same thing: the probability mass moves onto the letters and follows the content of the question instead of format cues and letter priors. But cross-entropy training keeps pushing the correct letter toward 1, so a fine-tuned model is sharp even when it is wrong. Temperature scaling then brings the overall sharpness in line with the actual accuracy. Only after both does 0.8 mean “right about eight times in ten”.

    Temperature Scaling#

    Temperature scaling divides the logits by a number T before the softmax.

    LogitsProbabilities
    T = 14, 2, 1, 00.83, 0.11, 0.04, 0.02
    T = 22, 1, 0.5, 00.58, 0.21, 0.13, 0.08

    The order does not change, so accuracy does not change. Only the sharpness does. A larger T flattens the distribution, a smaller one sharpens it, and T = 1 leaves it alone. For Noul, with two options, this is the same as a sigmoid of the logit difference divided by T.

    T is fitted on a held-out calibration set by minimizing the negative log-likelihood, which is lowest exactly when stated probabilities match real frequencies. It is a one-dimensional search over a few hundred to a few thousand items, and it is done separately for Choice, Noul and Score because they are over-confident by different amounts. Since the confidence formula is computed from p_max, changing T changes the confidence, and with it the usable threshold.

    Reported effects:

    ProjectECE before → after
    Laya0.466 → 0.081
    jev-from-scratch0.26 → 0.045
    Open Jev0.156 → 0.057

    Kev fitted T = 2.35 for a 0.8B model, which means its raw confidence was more than double what it should be.

    What temperature scaling cannot do:

    • It is monotonic, so it does not reorder items. If the model cannot tell its right answers from its wrong ones, the share that can be automated under a fixed error budget does not move. ECE and automation rate have to be reported separately.
    • One T is global. It cannot fix “this class runs high” or “the first option is favored”.
    • It does not transfer across datasets (measured in my rebuild).
    • T may only be fitted on the calibration set. Fitting it on validation or test data makes the reported ECE a cheat.
    • 4-bit quantization damages calibration. Calibrate the unquantized model first, and if it is quantized later, refit T on the quantized model.

    RLCD#

    TypeSafe says Jev is trained with RLCD (Reinforcement Learning for Calibrated Decisions), which targets calibration directly. The method is unpublished. Some reproductions imitate it with a proper scoring rule (Brier or log score) as the reward. Others argue that a softmax head with such a reward is mathematically close to plain cross-entropy supervision. Whether RL is needed is an open question. “SFT plus temperature scaling” is the community’s approximation, not Jev’s method.

    What Black-Box Probing Suggests#

    Jev’s Architecture Unmasked (Archer Hume, about 1,000 API probes) concludes:

    • Jev is most likely a causal decoder that only does prefill.
    • The state is encoded once into the KV cache. Each question is a separate suffix branch that cannot see the others: information hidden in a sibling question was visible 0.00 of the time, information in the state 0.90.
    • The readout is a softmax over the K allowed answers. 200 options are as fast as 2.
    • The confidence in the API response is the formula above.
    • The tokenizer matches none of 192 public tokenizers exactly. The closest is Qwen.

    A separate probe, krino, found that the surface form of an option (length, wording) explains about 43% of the variance in its probability (R² = 0.431). The author reads this as language-model log-probability leaking into the decision. R² is not a causal share, so this is an inference.

    How the Open Reproductions Do It#

    Three families have emerged.

    FamilyExamplesMethodScale
    Small decoder + LoRA + read logitsSemIf, Kev, train-jev, mpuig/system-oneLabel the options A to P and read the letter logits at the last position. Uses the decoder’s next-token predictionQwen 0.6B to 9B
    Encoder + scoring head at label positionsOpen Jev, Laya, Chinese-JevPut a marker before each option; a small head outputs one logit per marker; softmax within each questionModernBERT / mmBERT, 150M to 421M
    No trainingAny LLMRead the first-token logits directly, about 25 lines of code, no calibrationAny

    The Decoder Family#

    • SemIf trains nothing. It freezes Qwen3.5-4B and reads the letter logits, agreeing with Jev’s answers 0.845 of the time (Jev agrees with itself 0.883 across two runs). Its contribution is a standard protocol: encode the state once into the KV cache and run the questions as parallel suffixes. Later projects describe themselves as using “the SemIf protocol”. It runs on MLX, MPS and GGUF.
    • Kev has everything: training, evaluation, serving, and continued training on your own data for about a dollar. A frozen Qwen3.5 base with LoRA and a pointer head, so the number of options is not tied to letters. Several questions share one sequence, separated by a block causal mask, which reconstructs Jev’s parallelism. Its architecture follows the black-box article above. On new data sources its 27B version reports 0.889 against Jev’s 0.857.
    • train-jev is about distillation. It does not learn which option to pick. It uses 656K rows of Jev’s output distributions so that a 4B model learns, through KL divergence, how sure Jev is. Its 24-slot head is initialized from the letter rows of the output layer, so step 0 of training equals reading letter logits. More than 16 options are handled by knockout rounds.
    • mpuig/system-one is the smallest: Qwen3-0.6B with LoRA, native MLX. Its experiments found that adding a description to each option clearly raises confidence, that 8-bit quantization flips no argmax, and that data should be split by source group.

    The Encoder Family#

    • Open Jev is the cheapest: ModernBERT-base with 150M parameters, trained in 30 minutes on a Colab T4. It shows how an encoder gets labels that change at request time: the label text is part of the input, marked with <<l>>, and the scoring head looks only at that position.
    • Laya uses ModernBERT-large (about 420M), 33 ms on a T4 and 8 ms on MLX, trained with an RLCD-style proper-scoring reward. Zero-shot it is close to random (0.362, below the majority-class baseline) and passes Jev only after fine-tuning. A Japanese tester also found position bias in its Score type and truncation of option descriptions over 48 tokens. It shows both the ceiling and the weak spots of the encoder route.
    • Chinese-Jev is covered below.

    The Most Detailed Public Recipe#

    Marc Brooker’s Small Decisions: Engineering a Leading Model, which became AWS’s Decider 2B:

    • Qwen3.5-2B with the output layer (lm_head) removed. What is left can no longer write text and only understands it; he calls it the torso.
    • A pointer head of about a million parameters on top. He tried a 24-slot head first and dropped it for three reasons: at most 24 options, position bias, and no use of each option’s own hidden state.
    • LoRA r=16 for one epoch, cross-entropy on the gold answer, every item’s options shuffled.
    • KL self-distillation to prevent forgetting: keep a frozen copy of the original model and require the new model’s output to stay close to it. There are two KL terms, one against the original model and one against an earlier version, the second applied only to tasks that regressed.
    • 115K items: about 113K from public datasets and 2K hard cases generated by Qwen3.5-27B.
    • One temperature each for Noul, Choice and Score. p50 about 100 ms on an RTX 3090.

    His verdict on generalization: useful but not great. Switching to a 4B base made it worse.

    Four Ways to Read the Answer#

    The decoder family differs mostly in how the answer is read out.

    ReadoutHowStrengthCost
    Letter logitsReuse the model’s output layer; read the logits of " A" to " P"Works with little data, standard SFT tooling, same code scales to a larger baseAt most 16 options; depends on the tokenizer; letters carry their own prior
    24-slot head (train-jev)Replace the output layer with 24 fixed slots (2 Noul, 6 Score, 16 Choice), initialized from the letter rowsStarts out identical to letter logits, no tokenizer in the loopSlot k is option k, so the model can learn position instead of content
    Pointer head (Kev, Brooker)Compare each option’s hidden state with the hidden state at the answer positionAny number of options; scores come from the option textAbout a million new parameters trained from scratch; needs more data
    Encoder marker scoringA bidirectional encoder reads everything; a small network scores each markerAny number of options; small and cheapHead trained from scratch; the state sees the questions, so it cannot be cached and shared

    Letter Logits#

    The options are written into the input, not stored in the model. A prompt is the state, the question, an option list where each option has a letter in front, and an answer marker. The model outputs a distribution over the next token at that marker, and only the logits of the first n letters are kept, where n is the number of options in this question.

    “Dynamic” shows up in three places:

    • Option content comes from the input. The letter is a pointer to the k-th item of the list. B can be “refund” in this question and “cancel” in the next. What the model learns is to compare text, not that a letter means a class.
    • Option count comes from the input. Four options take four logits, eight take eight, and the rest are dropped. Same model, same forward pass.
    • Option order means nothing. Training shuffles every item, so “the first one is usually right” is not available.

    Compare a fine-tuned BERT: its output layer has a fixed N neurons, one per class, and adding a class means changing the layer and retraining. Here the output layer is always the whole vocabulary and the class information is entirely in the input.

    Dropping the other tokens renormalizes over the n letters. A trained model puts almost all its mass on the letters at that position, so little is lost. An untrained one loses a lot, which is one reason its probabilities cannot be trusted.

    Noul always has two options (A yes, B no) and Score has ordered levels (A to E from low to high). Neither is shuffled, because the order is the meaning.

    24-Slot Head#

    Think of it as a fixed workbench with 24 positions. It is very close to letter logits, just without the tokenizer. The weakness is the fixed mapping: slot 1 is option 1, so the model can pick up position instead of content, and it only looks at the answer position.

    Pointer Head#

    A pointer head does not care whether the options are called A, B and C. It scores how well each candidate matches the question, so the candidates can change with every task: email type today, customer mood tomorrow.

    It is added to the model, not swapped for it. The transformer’s hidden states can feed two paths.

    graph TD
    A[LLM body: transformer] --> B[Hidden states]
    B --> C[LM head: the original output layer]
    B --> D[Pointer head: the new scoring layer]
    C --> E[Generated text]
    D --> F[A score per candidate answer]

    The steps are: take vectors, compare them, turn scores into probabilities. A simplified four-dimensional example, for the message “The item still has not arrived. Please deal with it quickly.”

    VectorDot product with the question
    Question position0.8, 0.6, 0.2, 0.9
    Refund0.2, 0.8, 0.1, 0.30.93
    Change address0.1, 0.2, 0.9, 0.10.47
    Shipping complaint0.7, 0.6, 0.3, 0.81.70

    The score here is the plain dot product. A softmax over 0.93, 0.47 and 1.70 gives 26%, 17% and 57%, so “shipping complaint” wins.

    Adding the head does not mean retraining everything.

    WayWhat is trained
    Freeze the LLMOnly the pointer head
    LoRALoRA and the pointer head; most of the LLM stays frozen
    Full fine-tuningEverything

    Position bias does not vanish entirely, because an option’s hidden state still depends on where it sits in the sequence. It is just no longer tied to a fixed slot or letter.

    Encoder Marker Scoring#

    The base is a bidirectional encoder. Each option gets a marker in the input, and after the encoder has read the whole sequence, a small network outputs one logit at each marker.

    Email: My order is five days late.
Question: What kind of problem is this?
Candidates:
[shipping]
[refund]
[product quality]
    CandidateRaw scoreProbability
    Shipping3.284.5%
    Refund1.110.3%
    Product quality0.45.1%

    The encoder understands the text, the scoring head judges which option fits, and the softmax turns scores into relative probabilities. The softmax runs within one question. With two questions, “what kind of problem” (three options) and “does a person need to step in” (two options), the three and the two are normalized separately. Mixing all five would be wrong.

    How to Choose#

    Start with letter logits and measure permutation consistency on its own. If that is fine and 16 options are enough, there is no reason to change heads. If position bias is obvious or more options are needed, move to a pointer head. Changing the head only touches the readout and the loss; the base, LoRA, data pipeline, calibration and evaluation stay.

    Zero Training#

    Zero training means no fine-tuning at all: take a pretrained language model and use it as a decision model. The whole thing is about 25 lines of code and needs no training data.

    There are two ways to read the answer:

    • First-token logits. Read the option letters’ logits at the last position. This is exactly the trained readout, on an untrained model.
    • Completion log-likelihood. For each option, append its full text to the prompt and compute the log-probability of generating it, then take a softmax over the options. No letters and no option limit, but one forward pass per option, so several times slower.

    It works because pretraining corpora are full of multiple-choice questions, so the model already knows that a letter follows an option list. Larger models do better.

    It is not enough because:

    • There is no calibration, and ECE is usually poor.
    • It is sensitive to format. A different layout, or a letter with or without its leading space, changes the result a lot.
    • The prior for A is strong.
    • Small base models may not know to answer with a letter at that position, and the letter logits can be close to random.
    • “None of the above” is handled badly.

    As a baseline it is useful in two ways. If the zero-training result equals random guessing, the template or the tokens are probably mismatched, not the model too weak. And when it is the control for “did training help”, report a few-shot result as well as 0-shot. Comparing only with 0-shot overstates what training did, which I measured in my rebuild.

    Chinese-Jev in Detail#

    Chinese-Jev belongs to the encoder family, and its base is the one Laya released.

    graph TD
    A["Input: type · question · [MASK] option 1 · [MASK] option 2 · [MASK] option 3 · state"] --> B[mmBERT-base bidirectional encoder, about 320M parameters]
    B --> C[Two small transformer layers with a question-type embedding]
    C --> D["Scoring network at each [MASK]: one logit per option"]
    D --> E[Softmax within the question]

    Training objective: soft-label cross-entropy plus an RL-style calibration loss. The answer in the data is not a single option but a probability distribution, and the first term is the cross-entropy against it. The second term imitates RLCD:

    1. Sample. Add random noise to the logits several times, say eight, to get eight slightly different distributions. This is the “group of answers”.
    2. Score. Rate each distribution with strictly proper scoring rules (log score plus spherical score; ordered Score questions also subtract a ranked probability score penalty).
    3. Advantage. Subtract the group’s mean score and divide by its standard deviation. Above the mean is a good sample, below is a bad one. This is the GRPO trick: the group mean is the baseline, so no value network is needed.
    4. Update. Push the model toward the good samples and away from the bad ones.

    A strictly proper scoring rule gives the highest score only for reporting the true belief; sharpening toward the argmax is penalized. So this term optimizes calibration during training instead of patching it afterward with a temperature. A temperature per question type is still fitted at the end and stored in the model.

    Data. Ten million general items, fine-tuning for three domains (medical, legal, everyday), and 308K items of CJ-Bench held out for evaluation.

    Pipeline. Four stages: prepare, train, calibrate, evaluate. Prepare tokenizes everything once into a cache and measures how many tokens the option part can take, and every later run reuses the cache.

    Is It Just SFT on One Token?#

    For the decoder family, yes: training is ordinary supervised fine-tuning where the completion is a single letter. But four things turn that into a System One model.

    1. The output is a distribution, not a token. Nothing is sampled. The probabilities over the allowed letters are the product.
    2. The letter is only an index. Each training item shows 4 to 8 randomly drawn candidates in shuffled order, so the model has to read the option text. Without this, SFT still runs, but the model memorizes a fixed label set and “labels can change at request time” is lost.
    3. The probabilities need calibration after training, as above.
    4. The interface contract. Three primitives, option names and descriptions in the schema, the confidence formula, several questions per state. The model is one part of it.

    The training algorithm is the most standard piece. Most of the work is in the data: half of TypeSafe’s people work on data, and data takes up most of Brooker’s write-up.

    The Common Training Recipe#

    This is the recipe the decoder reproductions share, on English data. I used the same steps for Japanese, with different datasets; that run is in japanese-jev.

    1. Find datasets. Split them by license: those that allow training go into the training set, the rest are evaluation only. The two must not overlap.
    2. Rewrite into the three primitives. Every record becomes one text: state, question, option list, answer letter. For Choice, sample 4 to 8 options per item and shuffle them. Then cut into training, validation and calibration sets.
    3. SFT. LoRA, with the loss on the answer letter only. Run a few steps first to confirm it works.
    4. Calibrate. Fit the temperature on the calibration set. Skipping this leaves inflated probabilities and a poor ECE.
    5. Evaluate. Report three numbers together: the base model read out without training, the trained model uncalibrated, and the trained model calibrated. Without controls, “training helped” does not hold.

    Existing classification datasets all convert.

    PrimitiveDatasetRewriting rule
    Choicelegacy-datasets/banking77 (77 banking intents, 10K)The correct intent plus 3 to 7 sampled wrong ones, shuffled
    Choiceclinc_oos, config plus (150 intents plus out-of-scope)Same; for out-of-scope items the answer is other. Each item also yields a Noul (“does this message belong to one of the listed intents?”)
    Noulgoogle/boolq (passage plus yes/no question, 9K)State is the passage; options fixed as A yes, B no; not shuffled
    ScoreSetFit/sst5 (5-level sentiment, 8.5K)A to E from very negative to very positive; not shuffled
    ScoreYelp/yelp_review_full (1 to 5 stars, 5K taken)Same, 5 levels
    • Why sample negatives. There are 16 letters and Banking77 has 77 classes. With 4 to 8 candidates per item, the model learns to judge by the option text, not to remember a label set. This is where “labels can change at request time” comes from.
    • Why shuffle. Jev itself has a measured option-order bias. train-jev shuffles 30% of its Choice items; shuffling all of them is safer.
    • Split. A typical split is 16,000 training, 1,000 validation, 1,000 calibration and 1,000 test, about a third per primitive. The calibration set is only for fitting the temperature. Hold one whole source out of training (for example clinc_oos) to test generalization: in-distribution scores look much better than the real gap.
    • Ready-made alternatives. SargeDev/jev-distill-corpus-v3 (656K rows of Jev 1.13 output distributions, the data train-jev uses), LocalLLaMA/typed-decisions (1,016 items with annotator distributions), jaredpalmer/kev-suites (Kev’s evaluation sets).

    The template follows train-jev’s bare-v1. The prompt is this text, and the completion is one letter with a leading space, such as " B".

    [kind] choice
[state] I was charged twice for my flight to Berlin and nobody answers the phone.
[question] What is the main request?
[options]
A. refund: the customer wants money returned
B. rebooking: the customer wants a replacement flight
C. information: the customer wants information only
D. other: none of the above
[decision]:

    Lessons From the Reproductions#

    If only three stick: negative sampling plus shuffling is what makes the model judge by content; soft labels improve calibration more than temperature scaling does; out-of-distribution evaluation and control models decide whether a conclusion holds.

    Data design is the part most worth learning.

    • Sample negatives, so the model reads the options (jev-from-scratch, Kev).
    • Shuffle the options and move the answer letter with them. This is the main tool against position bias.
    • Give options descriptions, not single words. mpuig found bare-word options get clearly lower confidence; TypeSafe found Score levels written as situations work far better than numbers.
    • Add an other option and out-of-scope items, or irrelevant input gets confidently assigned to a class.
    • Use soft labels: mark ambiguous items 0.5 instead of 0 or 1, and add label smoothing. jev-from-scratch reports ECE 0.26 → 0.045 from this.
    • Add hard cases synthesized by a larger open model (Brooker: 2K of 115K).
    • Split by group, not by row, so several questions on the same passage land in the same split.

    Training.

    • LoRA r=16, learning rate 1e-4, one or two epochs. Nearly every project converges on these.
    • Loss on the answer token only.
    • KL self-distillation against the frozen base prevents forgetting (Brooker).
    • A larger base does not always help at once. Brooker got worse going from Qwen3-1.7B to 4B, which he attributes to a held-out set lacking the right questions, and better later with 8B. Fix data and evaluation before changing models.
    • Distillation has the best return: Abhi001vj used a 31B teacher to bring a 1.5B model’s ECE from 0.236 to 0.040 for under half a dollar.

    Calibration.

    • One temperature per primitive; ECE typically goes from above 0.2 to about 0.05.
    • Small models are over-confident by a factor of two or more by default.
    • 4-bit quantization breaks calibration and needs a refit; 8-bit is nearly lossless.
    • Temperature improves ECE but not the automation rate. Report them separately.
    • Whether an RL-style calibration loss beats cross-entropy plus temperature is open. Chinese-Jev and Laya use one; the author of qwen-rlcd argues it is mathematically close to direct supervision.

    Evaluation.

    • Report in-distribution and out-of-distribution separately. The real gap is on unseen sources.
    • Measure permutation consistency on its own: shuffle the same item several times and see whether the answer changes. Laya’s Score type was hurt by exactly this kind of position bias.
    • Use a full set of controls: an untrained baseline, existing open versions, the Jev API, a fine-tuned BERT. A number without a control means nothing.
    • Test failure modes on purpose. They do not show up in public datasets.
    • Vary the length of the correct option’s description and see how much the probability moves (the krino finding above).

    Engineering.

    • One config drives the whole pipeline; each run gets its own directory and records data and tokenizer fingerprints (Chinese-Jev).
    • Keep the interface identical to Jev’s, so existing clients, llama-server and Ollama connect directly.
    • Many projects share names. Go by the author.

    Inference and Serving#

    A trained model does not generate. Inference is one forward pass, the logits at the last position, only this question’s option letters, divided by the temperature, softmax. So the only requirement on the engine is that it hands over the next-token logits or log-probabilities, not just sampled text.

    Three Ways to Run It#

    1. Your own readout behind FastAPI. transformers with PEFT loads the LoRA directly (or mlx-lm on a Mac). Latency is tens of milliseconds and throughput is enough for evaluation and personal use. Use this for evaluation and a first server, because every step of the readout is under your control and problems are easy to find.
    2. vLLM. It supports this, with caveats:
      • It is built for generation, so ask for one token (max_tokens 1) with logprobs, and pick out the letters. A log-probability is the logit minus a constant, and the constant cancels in the softmax.
      • It returns only the top few tokens by default. Trained letters dominate, so they are there; an untrained baseline may need allowed_token_ids to restrict the output to the letters.
      • Apply the temperature yourself in the readout. Its temperature parameter only affects sampling.
      • LoRA loads directly as a PEFT adapter, or merge it into the base first, which is simpler.
      • Linux or WSL2 with an NVIDIA GPU only.
      • Its real value is concurrency: continuous batching and prefix caching. With one state and many questions, prefix caching encodes the state once. If the template puts other fields before the state, the cache hits less often.
      • On a single laptop GPU for your own evaluation, it gains little.
    3. GGUF with llama-server or Ollama. Merge the LoRA, convert to GGUF. Both now support /v1/systemone natively, so this is the easiest way to deploy for other people, on CPU and Mac as well. Use 8-bit and refit the temperature after quantizing.

    Get the numbers with the first, then choose between the third (compatible, cross-platform) and the second (throughput). Changing engines does not change the model, only how the logits are read. After switching, compare probabilities on the same samples.

    What “API-Compatible” Means#

    TypeSafe does not publish weights. It offers one HTTP endpoint, /v1/systemone, that takes a JSON request (a state and typed questions) and returns a JSON response (probabilities and a confidence per question). The user’s program only ever talks to that interface.

    Compatible means a small server of your own accepts exactly the same request and returns exactly the same response under the same path. Inside, it renders each question to the model’s input, reads the probabilities, applies the temperature, computes the confidence and fills in TypeSafe’s response format.

    Two reasons to do it. Switching costs nothing: any program already using Jev changes one address. And the ecosystem’s tools work as they are: the clients of other reproductions, llama-server and Ollama already speak this interface. The serving layer itself is mostly format conversion. The real work is in the readout and calibration.

    Sending Hundreds of Questions at Once#

    This is the second reason prefill beats generation: one forward pass processes the hundreds of tokens in a prompt in parallel, and it can process dozens of prompts in parallel too.

    • At the API level, one state comes with a set of questions. The server renders each question to its own prompt, runs one batched forward pass and returns each question’s probabilities.
    • At the model level, three things matter:
      • Left padding. Prompts of different lengths are padded on the left, so every sequence’s last position lines up at -1. Qwen uses rotary position embeddings, where positions are relative, so masked padding on the left does not affect the real tokens.
      • Keep only the last position’s logits. By default a forward pass computes logits for every position over the whole vocabulary (about 150K). A batch of 32 prompts of 512 tokens is close to 5 GB, several times the model itself. With logits_to_keep=1 that is cut to 1/512.
      • Each question has its own n. Take all sixteen letter logits, then slice by each question’s option count and run the softmax over its own options.

    Before any of this, confirm that each of " A" to " P" is a single token in the tokenizer. Otherwise the lookup returns half a letter.

    Why batching helps, step by step:

    • A model is a stack of matrices. A token is a vector that gets multiplied through them. A 512-token prompt is a 512-row matrix, and 512 rows are the same operation as one row, only taller. That is what “prefill is parallel” means.
    • Thirty-two prompts are 16,384 rows, still one operation over the same weights.
    • Attention is the only place that cares which rows belong together. A mask tells each position what it may look at, so 32 prompts in one batch do not interfere, and the result equals running them one by one.
    • A forward pass has two kinds of cost. A fixed cost per call (moving the weights from memory, launching GPU kernels, scheduling) and a real cost per row. A single prompt pays the fixed cost for 512 rows. Thirty-two prompts pay it once for 16,384. Throughput rises with batch size until the arithmetic itself saturates the GPU.
    • Padding makes a matrix. Rows must be equal length. Sorting by length before batching keeps the padding small.
    • Memory. The weights are fixed, the activations grow with batch × length, and the full-vocabulary logits are the largest part if they are not trimmed.

    Known Weak Points#

    From TypeSafe’s own “Model jaggedness” page and third-party tests:

    • Closed-set forcing. Irrelevant input still gets assigned to some option. An other option helps only partly; the recommended fix is a separate Noul that asks whether the input belongs to any listed class.
    • First-option bias.
    • Sensitivity to option wording. Score levels written as bare numbers got confidence 0.33; written as descriptions of each situation, 1.0.
    • Literal reading. Counting, date comparison and double negation are unreliable.
    • No few-shot support.
    • Weaker outside English. One third-party test on Japanese (biscuit) reports an 11-point drop on all-hiragana input and a 23.2% miss rate on Japanese prompt injection against 9.0% in English.

    When to Use It, and When Not#

    Fits. An e-commerce company sorts 50,000 support messages a day into refund, shipping, product and account. “My order has shown as shipped for five days but tracking has not updated” goes to shipping at 0.96, and the ticket is assigned to logistics. The question is clear, the answers are few, the task repeats, and nobody needs an explanation.

    Does not fit. Writing a 1,000-word marketing piece for a new coffee. It needs a lot of new language, there is no fixed answer set, and the output is the text itself.

    Looks like a fit but is not. “Is the invoice date later than the contract end date?” is a yes/no question, but date comparison is one of the documented weak points. Extract the two dates and compare them in code. Deterministic logic belongs in code, not in the model.

    Even for classification, results are unreliable when the classes are poorly defined, the input lacks the needed information, or the task needs multi-step planning.

    Worked Example: Agent Tool Selection#

    An agent has search, mail, calendar, a company database and file tools. The user says: “Check whether I am free tomorrow afternoon, and if so, set up a meeting.”

    1. State. The request and the current context.
    2. Questions.
    QuestionAllowed answers
    Task typesearch / schedule / email
    Does it need the calendar?yes / no

    Priority1 to 10

    {
  "task_type": "schedule",

    Taking It Further#

    After the two angles above I rebuilt a small version for Japanese: Qwen3-1.7B with LoRA, letter-logit readout and temperature calibration, trained on an 8 GB laptop GPU. The pipeline and full results are in japanese-jev. This section is about what happened after the plain rebuild worked. All numbers here are from my own runs on development test sets, with one random seed.

    Where the Plain Rebuild Stopped#

    LoRA on public Japanese data alone taught the model the answer format and little else. Against the untrained base model given four examples (4-shot), no unseen test set showed a difference that survived a paired test (|z| ≥ 2).

    Test set0-shot4-shotLoRA on public data
    JCommonsenseQA54.480.282.8
    MASSIVE intents (8-way)60.084.085.4

    What training did buy: accuracy on the trained tasks, stable answers when options are shuffled, and speed, since no examples have to be carried in the prompt.

    Two lessons came out of this that I did not expect.

    • Data design beat everything else. A thousand items aimed at a real gap moved more than tens of thousands of public items, a second synthetic batch, or a teacher model.
    • Checkpoint selection can hide the result. Continued training kept picking the checkpoint with the lowest validation loss on the old tasks, which was always near step 100. The pragmatics score I first reported (63.3) was that early checkpoint. Trained to the end it is 69.3, and the model is more over-confident.

    The synthetic training data and the self-built test sets share an author (Claude), so the gains on those sets are optimistic. Acceptance needs items written by a person.

    The distillation run produced one more thing for free: 9,510 items that Jev had answered, including the augmented variants. On those, Jev’s agreement with the original labels fell by about 8 points on average for all-hiragana rewrites (a third party measured 11 on its own test) and by about 3 points with an added irrelevant sentence. Full-width, half-width and reordered options made no measurable difference. These are different items from my own probes, so only the size of the drop can be compared: about 8 points for Jev against 13 to 47 for my model.

    Using Both Models Together#

    The local model’s confidence is good enough to route on. If it answers only when its confidence is at least 0.7 and sends the rest to Jev:

    Test setLocal onlyJev onlyAnswered locallyCombined accuracy
    MASSIVE86.093.473%92.2
    JCommonsenseQA81.497.058%94.4
    Pragmatics69.389.076%78.3

    On MASSIVE about 70% of API calls disappear and accuracy stays close to Jev alone. Where the local model is weak, as on pragmatics, routing helps much less. The threshold was chosen after the fact on the same items, so this shows the order of magnitude, not a deployment result.

    This is the same pattern Jev is sold for, one level down: a cheap model answers what it is sure of, and only the uncertain cases take the expensive path.

    If It Had to Scale Ten Times#

    • 550K training rows. Training time on the laptop grows about tenfold, so it moves to a cloud GPU. The evaluation scripts, paired tests and reports carry over unchanged.
    • More than 16 options. Letter logits run out; switch to a pointer head or knockout rounds.
    • High request volume. Use an engine such as vLLM for batching and prefix caching. The current template puts the question type before the state, which weakens prefix caching, so the template has to change and the model has to be retrained.
    • Synthetic data. Move to batch generation with human spot checks.
