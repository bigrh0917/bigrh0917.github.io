    japanese-jev: A Japanese System One Decision Model on a Laptop GPU#

    #LLM; #LoRA; #Evaluation; #Calibration; #Japanese

    An unofficial reproduction of a “System One” (Jev-style) typed decision model for Japanese. It does not generate text: given a text, a question and a list of options, it returns a probability for each option from a single forward pass.

    Repository: https://github.com/bigrh0917/japanese-jev-release · Weights: 1.7B, 0.6B

    Not affiliated with TypeSafe AI or Jev.

    graph TD
    A[Public Japanese datasets] --> B[Convert to choice / yes-no / ordinal template]
    S[1,109 synthetic items: negation, indirect refusals, honorifics] --> C
    B --> C[LoRA fine-tuning of Qwen3-1.7B-Base]
    C --> D[Read option-letter logits at the last position]
    D --> E[Temperature scaling]
    E --> F[Evaluation: accuracy, ECE, paired comparisons]
    F --> G[FastAPI endpoint]

    Project Overview#

    Jev is a closed model from TypeSafe AI that answers typed questions (pick one option, yes or no, rate on a scale) with probabilities instead of generated text. Its documentation says accuracy is lower outside English, so I built a small model of the same kind for Japanese to see how far a laptop could get. What Jev is and why it matters is in a separate note: What Is Jev?

    The model is Qwen3-1.7B-Base with a LoRA adapter (r=16). Training completions are a single option-letter token; inference reads only those letters’ logits at the last position and applies a softmax, so there is no decoding loop. Everything was trained on one RTX 4060 Laptop GPU (8 GB). A 0.6B version trained with the same recipe is also released.

    Goals and Hypotheses#

    When Jev came out, a common reaction was “this is just a classifier”. If that is true, a 1 to 2B model on a laptop should be able to do it. I wanted to check that, and to see where the method breaks when it is moved to Japanese.

    The constraints:

    • The method is not public. No weights, paper, data or training code. The structure has to be inferred from open reproductions and other people’s black-box probes.
    • 8 GB of GPU memory, one person, about a week. Only models under 2B, and only with LoRA.
    • Japanese data is scarce and restricted. Public classification data is small and comes in different formats. livedoor (CC BY-ND) and WRIME (research only) can be used for evaluation but not for training. Public data has almost no items where the literal and the intended meaning differ.
    • Evaluation is easy to fool. There is no ready-made Japanese evaluation for this kind of model, and accuracy on 500 items carries ±3 to 4 points of error.

    The first goal was a Japanese model that answers choice, yes/no and ordinal questions, with temperature-calibrated probabilities, behind a /v1/systemone endpoint. After the first round I made it measurable:

    GoalStatus
    Pragmatics (self-built set) at 75% or above69.3%, not reached
    Ordinal questions clearly above chance on a scale the model has never seen (WRIME)Not reached: 67 on a balanced measure where chance is 50; still the weakest type
    Numbers on a sealed test setThe set exists and has not been run
    A comparison with Jev itself on the same itemsDone, 1,600 items

    A change counts as an improvement only if a paired comparison with the untrained base model at 4-shot gives |z| ≥ 2, and JCommonsenseQA does not drop.

    Highlights#

    • Speed: about 25 ms per question locally, roughly 14x faster than having the same model generate a JSON answer (344 ms).
    • An honest baseline: against a 0-shot baseline, training looked like +27 points on JCommonsenseQA; against 4-shot it was +1. On unseen tasks, LoRA on public data alone bought speed and format stability, not accuracy.
    • Targeted data worked: adding 1,109 synthetic items for what public data lacks (negation pairs, indirect refusals, honorific relationships) raised pragmatics from 53 to 69 and negation from 81 to 97.
    • Usable confidence: answering locally only when confidence is at least 0.7 and sending the rest to Jev would skip about 73% of API calls on MASSIVE at 92.2% combined accuracy, against 93.4% for Jev alone.
    • Three Japanese evaluation sets (600 items) for pragmatics, negation and knowledge, released under CC BY 4.0.

    How the Rebuild Works#

    Four stages run from one config file, and a server sits on top of the result:

    build → data/*.jsonl → train → adapters → calibrate → temperature.json → evaluate → evaluation.json

    1. One Template for Three Question Types#

    Every item, whatever its type, becomes one block of text. The model’s only job is to put the right letter after [decision]:.

    [kind] choice
[state] 先週注文した商品がまだ届きません。配送状況を教えてください。
[question] この文章の主な目的はどれですか。
[options]
A. 依頼: 何かをしてほしいと頼んでいる
B. 質問: 情報を尋ねている
C. 苦情: 不満を訴えている
D. 感謝: お礼を伝えている
[decision]:
    TypeOptionsShuffled?
    choiceUp to 16 named options, each optionally with a short descriptionYes
    noul (yes / no)Always A. yes, B. noNo
    score (ordinal)Levels from lowest to highestNo, the order is the scale

    Training, inference and the API server call the same render() function. The model is very sensitive to this format: one extra space or a missing newline and accuracy drops to chance without any error.

    2. Data#

    Public Japanese datasets are rewritten into the three types, about 55,000 rows in total. All six have licenses that allow training and releasing weights.

    JSTS6-level score (similarity)CC BY-SA 4.012,451
    KUCIchoice, 4-way; half the items borrow 4 to 8 wrong options from other items to reach 8 to 12CC BY-SA 4.010,000
    PAWS-X (Japanese)noul (same meaning?)Open, with attribution10,000
    MewsC-16 (Japanese)choice, once with all 12 topics and once with a 6-topic subsetCC BY 2.5 and others3,968

    The rules that shaped it:

    • Training and evaluation use different datasets. JCommonsenseQA, MASSIVE, livedoor news, WRIME and JCoLA are evaluation-only, and the build fails if one is listed as a training source. livedoor and WRIME could not be used for training anyway because of their licenses.
    • Duplicates are removed, and when the same item appears with conflicting answers the whole group is dropped.
    • Each question type is capped at 16,000 rows, taken from the sources in turn so that one large dataset does not fill the cap.
    • Choice options are shuffled, and the same source appears with different option sets. The model has to read the option text. It cannot memorize a label set or a position.
    • Many-option items are included on purpose. The first data version had at most five options per item, so the model had never seen the letters after E.
    • Splits are by group. Validation (1,000 rows) and calibration (1,000 rows) are cut from the training pool by source text, so a validation item never has a sibling in the training set.
    • Augmented rows are added at a ratio of 25%: all-hiragana, full-width and half-width variants, an added irrelevant sentence, and permuted options.
    • SIB-200 (7 topics, 1,004 items) is used only in calibration, to fit temperatures. It is neither trained on nor evaluated on.

    3. Training#

    Plain supervised fine-tuning with TRL’s SFTTrainer. The loss is computed on the completion only, which is one letter token. Otherwise it is diluted by several hundred prompt tokens and the model learns nothing about the decision.

    SettingValue
    LoRAr=16, alpha=32, dropout 0.05, on q/k/v/o and the gate/up/down projections. PEFT’s default for Qwen3 is q and v only, so the seven modules have to be listed
    Learning rate1e-4, cosine schedule, 3% warmup
    Batch4 with gradient accumulation 2 (1.7B on 8 GB)
    Sequence length, precision512 tokens, bf16, gradient checkpointing
    CheckpointsEvaluated and saved every 200 steps; the one with the lowest validation loss is kept. Continued training later switched to the last checkpoint
    Continued training on synthetic data5e-5: the synthetic items five times over plus 5,000 earlier items to prevent forgetting
    Distillation variant0.5 × KL(Jev ‖ student) + 0.5 × cross-entropy on the correct letter, computed over the option letters only
    RunModelDataSteps and time
    Smoke test0.6BA first cut of the public data1,500 steps, 10 minutes, only to confirm the pipeline works end to end
    Main training0.6B and 1.7BAbout 55,000 rows, group splits1 epoch for 0.6B, 2 epochs for 1.7B (the longest run, overnight)
    Continued, first synthetic batch1.7B and 0.6BSynthetic × 5 + 5,000 earlier items1,319 steps, about 26 minutes for 1.7B
    Continued, second and third batches1.7B and 0.6BFirst and second batches × 3 each + 6,000 earlier items; the third adds 2,300 JCoLA sentences1,903 and 2,191 steps, about an hour each for 1.7B
    Distillation comparison0.6B9,510 items1,189 steps, about 19 minutes each

    Reading the loss. Because the completion is one token, the loss is the negative log-probability of the correct letter, which makes it easy to interpret. These are rules of thumb for this recipe:

    • A starting value of 2 to 6 is normal, since the base model does not know it should answer with a letter. It should fall below 1 within the first 100 to 200 steps.
    • A healthy final value is about 0.3 to 0.6. It does not reach 0 because some items are ambiguous.
    • Stuck near ln(K), about 1.4 to 2.1 for 4 to 8 options, means the model is guessing uniformly. That is almost always a template or token mismatch.
    • Validation loss rising while training loss keeps falling is overfitting. Take the checkpoint before the rise.
    • In TRL’s log, loss is the training loss, eval_loss is on the validation set, and mean_token_accuracy is the share of letters answered correctly. The logged loss averages over the letter and the end token, so it is lower than a letter-only loss.
    • A training loss far below the validation loss (0.11 against 0.32 in continued training) means the data has been memorized, usually because a small set was repeated too many times. This is why the later batches were repeated three times, not five.

    4. Readout#

    Inference runs one forward pass and looks at the last position only. The output there is a score for every token in the vocabulary, about 150,000 of them. Of those, only the tokens " A" to " P" matter, and of those only the first n, where n is the number of options in this question. Those n numbers go through a softmax.

    Two details decide whether this works at all:

    • The letter tokens include the leading space. Training writes " A", so the readout must look up the id of " A". Looking up "A" reads a different token and the result is close to random.
    • Long inputs are shortened in the state only. The question, the options and the [decision]: marker must survive intact.

    Since the letter is only an index into the option list, the same model handles four options or twelve, and the options can change on every request.

    5. Calibration#

    After training the model is over-confident. Temperatures are fitted on the calibration set by minimizing the negative log-likelihood (a one-dimensional search between 0.3 and 6), and the logits are divided by them before the softmax. There is one per question type, and within a type a separate one per option-count bucket (2, 3 to 5, 6 to 16) when the bucket has at least 50 items. The final per-type temperatures are 2.09 (choice), 1.80 (noul) and 1.64 (score).

    On the training sources this lowers ECE from 0.114 to 0.043. The same temperatures do not carry over to other datasets: on unseen test sets they sometimes made ECE worse, and fitting on a different dataset (SIB-200) was worse still. So in-distribution results are reported calibrated and out-of-distribution results uncalibrated, and a deployment should refit the temperature on 200 to 500 of its own examples. Changing the calibration set does not need retraining. It is a refit of a few minutes.

    6. Evaluation#

    Accuracy alone is not enough for a model whose product is a probability.

    MetricWhy
    Accuracy with a 95% interval500 items carry about ±3 to 4 points of error
    Paired comparison on the same items (z; a difference counts at |z| ≥ 2)More reliable than comparing two accuracies
    ECE (15 bins), Brier, NLLWhether the probabilities can be trusted
    Automation rate at a 2% or 5% error budgetWhat a business cares about: how much can be handled automatically
    Permutation consistencyWhether the answer survives shuffling the options four times
    p50 latencySpeed is the selling point of this design
    Balanced accuracy on WRIMEPlain accuracy is fooled by always answering the lowest level

    The controls are the untrained base model at 0-shot and 4-shot, and the Jev API on the same 1,600 items (cost: $0.027). Other people’s reproduction numbers are only an order-of-magnitude reference, since their items and option counts differ.

    Checks on the evaluation itself:

    • Blank the input. Removing the state and keeping only the question and options sends every test set back to chance, so none of them can be answered from the options alone.
    • Intervals and baselines. A script prints confidence intervals, the random and majority-class baselines, paired tests, and a list of suspicious items.
    • Label review. 49 suspicious knowledge items were checked by hand. In three categories where Jev also did badly (counters, kanji readings, correct honorific use), 4 counter items and 6 reading items turned out to be ambiguous or to have a flawed option, and their wording was revised. The item count stayed the same. One ordinal scale (how likely a promise is to be kept) was not mislabeled but too fine: one sentence cannot separate “almost none” from “low”.
    • Speed re-measured after finding that earlier latencies were taken with GPU memory filled by my own code.

    Comparing with the Jev API fairly:

    My typeWhat is sent to JevWhat comes back
    choicecriteria as option name → descriptionThe selected option and a probability per option
    noulinstructions as the questionThe probability of “yes”
    scorecriteria as the ordered list of levelsA score and a probability per level

    The highest-probability option is taken as the answer and stored in the same prediction format as my own model, so the same script does the paired comparison. Accuracy, ECE and automation rate can be compared, because the items and options are identical. Latency cannot, because one side includes a network round trip. Items whose licenses do not allow it (WRIME, livedoor) and the sealed set were not sent. Jev scored 97.0 on JCommonsenseQA, close to the 97.8 someone else reported, which suggests the hookup is right.

    Ablations: 0.6B against 1.7B; 0-shot, 4-shot and LoRA; distillation with and without Jev’s probabilities; the three synthetic batches (the third against the second is a clean comparison, differing only in JCoLA); LoRA merged against unmerged.

    7. Serving and Speed#

    A small FastAPI server exposes /v1/systemone with the same request and response shape as Jev’s API: one state, several typed questions, probabilities and a confidence back. Each question is rendered to its own prompt and gets its own forward pass.

    SettingPer question
    1.7B, one question at a time (LoRA merged)25 ms
    1.7B, batches of 812 ms
    Untrained base model + 4 examples94 ms
    Same model generating a JSON answer (15 tokens)344 ms
    Jev API, one question at a time (from Japan, including network)377 ms

    Measured on JCommonsenseQA, 200 items × 3 rounds, on the RTX 4060 Laptop GPU. Most of Jev’s 377 ms is network time, and Jev can answer several questions in one request, so this is not a comparison of model speed. What it shows is that running locally removes the round trip, and that reading probabilities is an order of magnitude faster than generating an answer.

    Other measurements on the 1.7B model:

    • Permutation consistency. The share of items answered the same way after shuffling the options went from 0.69 to 0.93 with training.
    • Robustness. Rewriting the input in all hiragana costs 13 to 47 points. Adding an irrelevant sentence at the end stays within ±3 points on every set.
    • Over-confidence. Trained to the end, the temperatures are 1.6 to 2.1, so the raw probabilities must be recalibrated before use.

    Implementation Details That Mattered#

    • Compute logits for the last position only. The first version produced vocabulary-sized logits for every position, which filled the 8 GB of memory and more than doubled every latency I had measured. Fixing it is what brought a question down to 25 ms.
    • Merge the LoRA weights before serving. Unmerged is about 75% slower (44 ms against 25 ms).
    • Resume from checkpoints. Laptop sleep stalled one overnight run and an automatic Windows update killed another.
    • Check the data after every build: answer distribution, whether options were shuffled, and whether any evaluation text leaked into training.

    Three rules that cannot be bent:

    1. The text format in training and in inference must be identical. The model learns that at the end of text in this exact format the next token is the answer letter. Any difference (one more space, one fewer newline, a letter with or without its leading space) and accuracy falls to chance, with no error.
    2. When an input is too long, shorten the state only. The model answers at the position after the option list and the decision marker. Shorten the state to fit the budget before assembling the text; do not cut the assembled text from the end.
    3. Training, calibration and evaluation sets do not overlap, and each has one job. Training updates the weights. Calibration only fits the temperature. Evaluation only produces the final numbers and never changes, so versions stay comparable.

    The order I worked in: one item all the way through first, checking the assembled text, the token ids and the logits at the last position. Then a few training steps, to confirm the loss falls and the saved weights load. Then the full run.

    What I Learned#

    • The control decides the conclusion. The same model is “+27 points” against 0-shot and “no significant difference” against 4-shot.
    • Data design matters more than training time. Training longer moved little. Many-option data and targeted synthetic data are what changed the results.
    • Confirm the test set is sound before believing a score.
    • Write down the experiments that did nothing.

    What Did Not Work#

    • Distilling from Jev’s probabilities: no measurable difference from training on hard labels over the same 9,510 items. Jev agreed with the original labels on 73% of them, from 45% on JSTS to 95% on the synthetic items.
    • A broader second batch of synthetic data (1,965 items across nine everyday scenarios): no measurable gain.
    • Adding JCoLA training sentences (2,300): acceptability judgments stayed near chance.
    • Training on public data alone made no measurable difference from 4-shot on unseen tasks.
    • Trained to the end, the model is over-confident, and calibrated temperatures make out-of-distribution ECE worse.

    More on these and on what could come next: Taking It Further.

    Mistakes I Made#

    1. Reported 95% on a test set without looking at its distribution. The 500 livedoor items were all from one category, so always answering that category scores 95%. With stratified sampling it is about 50%.
    2. Kept the old checkpoint rule in continued training. Selecting by validation loss on the old tasks stopped all three variants between steps 100 and 800, so most of the training went unused. The “pragmatics 63.3” I first reported was step 100. Trained to the end it is 69.3, at the cost of a more over-confident model.
    3. Changed three things at once. The second synthetic batch differed from the first in data, repetition count and the earlier items mixed in, so the two cannot be compared cleanly.
    4. Measured speed with memory full. The code computed vocabulary-sized logits for every position, which filled GPU memory and more than doubled the latencies.
    5. Let one author write both the training items and the test items. The gains on pragmatics and negation include some “same question style”.

    Also fixed along the way: a conclusion that “training broke double negation” came from 20 skewed items, and 100 minimal pairs showed the base model was weak there to begin with. The first validation set shared source texts with the training set, which made it optimistic until the splits were grouped.

    If I Did It Again#

    • Build the evaluation sets, the sealed set and the 4-shot control first, and check the test distributions, before the first training run.
    • Have a person write the acceptance items, not the author of the training data.
    • Run several random seeds from the start.
    • In continued training, use the last checkpoint, or select on a validation set for the new task.
    • Change strictly one thing at a time.

    Writing Synthetic Data#

    • Decide what to fill first. It only helps where public data has nothing and the task needs it.
    • Do not look at the test items while writing training items, and check for overlap by program afterward. Do not patch the test set’s errors.
    • The training and test items should not share an author. This is the largest hole in this project.
    • Control the answer distribution: cap the majority class, shuffle option positions, keep yes and no roughly even.
    • Minimal pairs in groups (affirmative, negative and double negative differing in one place) help more than scattered items.
    • Do not force a label on an item you are unsure about. Describe each level of a scale in words, and do not make the levels too fine.
    • Keep the range broad, with several phrasings for the same question.
    • A small synthetic set has to be repeated, but too many repetitions get memorized. Mix in earlier items so old tasks are not forgotten.
    • Record the source and license. Fix the seed in the generator so it reproduces the same output, print statistics after generating, and read through the result.
    • Accept with a control, change one thing at a time, and record it when nothing happens.

    Troubleshooting#

    Common failures of this recipe, collected while preparing and running it:

    SymptomCauseFix
    Loss stuck near ln(K), accuracy at chanceThe letter token does not match: training wrote " A" and the readout looks up "A", or the template has an extra newline at the endUse one render() for training and readout; encode the prompt plus " A" and check the last token id against the stored letter id
    Loss barely falls, but is not at ln(K)The prompt is not masked out of the loss, or the learning rate is too small (1e-5 is for full fine-tuning; LoRA wants 1e-4)Confirm the loss is completion-only; set 1e-4
    CUDA out of memory on 8 GBBatch or sequence too long; model loaded in fp32; another program holds memoryBatch 4 with gradient accumulation 2; shorten the maximum length to 384; confirm bf16; check nvidia-smi
    PyTorch on a Mac reports an unsupported MPS operator or a bf16 problemThe MPS backend is incompleteUse MLX for both training and inference on a Mac; if PyTorch is unavoidable, enable the MPS fallback and use fp32
    ModernBERT (the encoder route) slower than expected on a MacIts speed depends on FlashAttention removing padding, which MPS lacksRun the encoder route on an NVIDIA GPU or Colab; on a Mac use the sdpa attention implementation and accept the slowdown
    ECE above 0.2 before calibrationNormal. Small fine-tuned models are over-confidentThis is what fitting T is for. Fit it on the calibration set only, never on the test set
    ECE worse after quantizing a calibrated model4-bit quantization changes the logit distributionRefit T after quantizing. 8-bit is nearly lossless; re-measure 4-bit
    The answer changes when options are reorderedOption-order biasShuffle the training data; add permutation consistency to the evaluation
    Test is good, a held-out source is much worseA normal out-of-distribution drop, or options without descriptionsAdd a one-line description to each option; mix more sources into training
    Irrelevant input is confidently assigned to a classClosed-set forcing, which Jev has tooAdd an other option with out-of-scope training items, and a separate yes/no gate. Both together are safest
    The Qwen3 base outputs <think> or a chat formatAn instruct model or a chat template is in useUse the Base model and plain text, with no chat template anywhere
    The same passage appears in training and testOne passage has several questionsGroup by passage before splitting

    Limitations#

    • All-hiragana input drops accuracy by 13 to 47 points.
    • Ordinal (score) questions are the weakest type: 63% even on the training sources.
    • It cannot do kinds of tasks it was not trained on. JCoLA is close to chance.
    • Knowledge questions do not improve with this kind of training.
    • At most 16 options per question, because the readout uses the letters A to P.
    • One forward pass per question; Jev answers several questions against one state in a single request.
    • Jev itself is clearly stronger on the same items: 16 points on commonsense, 20 on pragmatics and more than 30 on knowledge.

    Still open:

    • Several random seeds, the sealed set, and acceptance items written by a person.
    • About 1% of items get a different answer in a batch than alone.
    • Four source texts appear in both the test set and the sealed set.
    • The 0.6B speed has not been re-measured after the memory fix, and the Mac training code has not been run on a real machine.
